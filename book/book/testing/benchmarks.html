molla — Rust + WGPU Physics Engine

Benchmarks

molla ships criterion benches in the crate that owns the measured functionality. Most physics benches now live under crates/molla-solvers/benches/, geometry benches under crates/molla-geometry/benches/, kernel benches under crates/molla-kernels/benches/, sensor benches under crates/molla-sensors/benches/, and facade/product step benches under crates/molla/benches/. They serve two purposes:

  1. Tracking perf regressions — criterion saves baseline times and reports relative changes per run.
  2. Comparing CPU vs GPU — paired _cpu_vs_gpu benches run both backends in one criterion group so the reports print side-by-side.

This chapter documents what each bench family measures and how to read the output.

Running

The Makefile exposes three convenience targets:

make bench-cpu              # CPU step bench
make bench-gpu              # GPU step bench (needs wgpu adapter)
make bench-featherstone     # CPU-vs-GPU Featherstone in one criterion group

To run a specific bench:

nixVulkan cargo bench -p molla-solvers --bench bench_xpbd_pile_gpu --features gpu

Each bench’s name maps 1:1 to a benches/<name>.rs file in the owning crate. The owning crate’s Cargo.toml [[bench]] sections set required-features = ["gpu"] for GPU benches so they only attempt to build when the feature is on.

Reading criterion output

A typical bench output:

xpbd_pile/cpu_1000      time:   [3.4231 ms 3.4567 ms 3.4923 ms]
xpbd_pile/gpu_1000      time:   [0.4123 ms 0.4256 ms 0.4401 ms]
                        change: [-2.1% -1.4% -0.7%]   (p = 0.03)
                        Performance has improved.
  • The first row reports the CPU bench at N=1000.
  • The second row reports the GPU bench at N=1000.
  • change is relative to the saved baseline (criterion stores baselines under target/criterion/).
  • p = 0.03 is the t-test confidence — values below 0.05 are considered significant.

For the paired _cpu_vs_gpu benches, criterion groups CPU and GPU samples on the same plot so the wall-clock ratio is one chart read.

Async / readback caveats

The GPU benches measure end-to-end wall time including wgpu submit + readback. This matters because:

  • Many GPU kernels are sub-millisecond on the device itself, but the pollster::block_on(device.poll(MaintainBase::Wait)) round trip can dwarf the kernel cost.
  • Persistent-buffer dispatchers (Stage 24d.2 MPM, Stage 41 v6 FEM) amortise the submit cost across substeps; the bench numbers reflect that.

If a bench number looks suspiciously slow, the most common cause is per-substep readback. The fix is the persistent-buffer pattern documented in design rules.
