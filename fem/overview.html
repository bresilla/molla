molla — Rust + WGPU Physics Engine

Finite-Element Method — overview

Molla ships a substantial, layered Finite-Element Method (FEM) framework under crates/molla/src/fem/. It is the single largest physical-modelling subsystem in the engine and is where molla materially leads its ancestor projects: Nvidia’s newton has no FEM module at all (it is a purely particle / soft-rigid solver), and warp ships only the bare infrastructure needed for the newton examples. Molla’s FEM stack covers heat / Poisson, linear elasticity, hyperelasticity (St Venant– Kirchhoff and symmetric-Dirichlet distortion), wave propagation, incompressible Stokes / Navier–Stokes (Taylor–Hood mixed elements), Discontinuous Galerkin advection / shallow-water, eddy currents (time-harmonic Maxwell), magnetostatics (H(curl) Nedelec elements), adaptive mesh refinement with hanging-node constraints, cross-mesh L²-projection (mortar), Signorini contact via Lagrange multipliers, multigrid and AMS preconditioning, and an APIC FEM-MPM hybrid coupling — most of which have a matching GPU port behind the gpu Cargo feature.

This chapter set documents that machinery. Read it top-to-bottom for a walking tour, or jump to a specific topic via the cross-links.

The five “core” chapters mirror this layering:

  • mesh — FemMesh + FemCell::{Tri, Tet}, grid builders, Gmsh MSH 4.1 import, compute_edges.
  • quadrature — Gauss rules: 1 / 3 / 6-pt on triangles, 1 / 4 / 5 / 11-pt on tets, plus 3D-tri surface rules used by the Stage 47 v3 nonconforming projection.
  • elements — per-cell B^T D B kernels: mass, stiffness (Laplacian / wave / α∇²), linear elasticity, St Venant– Kirchhoff stress, convection, SUPG stabilisation, symmetric-Dirichlet distortion energy.
  • assembly — closure-driven assemble_global that scatters local matrices into a BsrMatrix (B = 1, CSR-shaped).
  • function spaces — exposed via the FunctionSpace enum: P1Nodal, P1Vector { dim }, P2Nodal, P2Vector { dim }, DGNodal { degree }, NedelecEdge { order }.

The five “physics” chapter clusters layer on top:

  • Boundary conditions — strong Dirichlet (symmetric reduction), NeumannTraction integration, DG Nitsche weak-Dirichlet.
  • Solvers — steady-state (CG + PCG), transient (backward Euler), wave (Newmark-β), Newton–Raphson, GPU-resident steppers, distortion-minimisation, optional russell direct LU.
  • P2 nodal elements and the DG cluster — higher-order continuous and discontinuous bases.
  • Stokes / Navier–Stokes — Taylor–Hood mixed elements + Uzawa-CG and the FFT-Poisson alternative.
  • APIC coupling, adjoint, AMR, elasticity-GPU, magnetostatics, eddy currents, multigrid / AMG, nonconforming, Signorini contact, friction — each its own self-contained chapter.

Storage convention

Every assembled global matrix lives in crate::math::sparse::BsrMatrix with block size B = 1 — i.e. a plain CSR. The choice is deliberate: CG / GMRES / PCG only need matvec, the BsrMatrix builder from_scalar_triplets already dedupes coincident (row, col) entries, and the GPU port (FemGpuData) is a direct mirror of the same flat arrays. Vector-valued fields are stored interleaved — DoF v · d + c for vertex v, component c, dim d — so the scalar CSR row count equals n_vertices · d for vector spaces.

The element visitor returns a dense Vec<Vec<Real>> of size (n_v · d) × (n_v · d) per cell. This is intentionally simple at the expense of allocator churn — Stage 36.5 moved the hot per-cell payload to a packed [Real; 144] style buffer on the GPU side, but the CPU visitor API kept the dense form for readability.

Why molla leads here

xtra/newton/ (the Nvidia reference under xtra/) has no FEM solver — it is a particle / rigid-body / cloth engine that delegates all field problems to a hand-rolled BVH + Position-Based-Dynamics loop. xtra/warp/ ships compute primitives (sparse matvec, FFT, BVH, mesh queries) but no element kernels and no assembly machinery.

The molla FEM stack is therefore architecturally novel within the project family. Where the reference codebases overlap with molla (particles, rigid bodies, contact graphs, MPM) we copy the Newton / Warp algorithms verbatim. Where they don’t — every chapter in this section — we wrote the algorithm from textbook references (Hughes, Zienkiewicz, Wriggers for contact, Cockburn-Karniadakis-Shu for DG, Toro for SWE, Hiptmair-Xu for AMS, Solin for Nedelec) and validated against analytic / convergence-rate tests. Every chapter that follows calls out the textbook reference and the test that locks the implementation in.
